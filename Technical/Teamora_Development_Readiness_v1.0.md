## 1. Database setup

Nothing in the BRD/PRD, TDD or charter names a database or says how local development should connect to one.
TDD §17.2 fixes only the engine: **PostgreSQL with the pgvector extension**, Row-Level Security, and Patroni HA in production.
The decisions below fill that gap. They were **confirmed on 2026-09-23** and are also recorded in the charter (`Teamora_Technical_Stack_Charter_v1.1.md`, "Database rules").

### 1.1 Database rules (decided)

1. **Local development uses a local database.** It runs on the developer's own machine (Machine A: native PostgreSQL 18).
2. **Staging uses the real remote database.** It's a PostgreSQL instance on the staging server, managed by Coolify, and only the deployed staging application connects to it. Production gets its own separate remote instance the same way.
3. **The database name is `teamora` in every environment.** Local, CI, staging and production all use the same name. Schema names and role names are identical everywhere too.
4. **Only the credentials change between environments:** host, port, user passwords, and therefore the connection string. They come from environment variables: a local `.env` on the developer machine, and Coolify environment variables on staging and production. They are never committed to Git.
5. Developer machines never hold staging or production credentials (SOP §8.1). Code runs against staging only by being deployed there through the pipeline.

| Environment | Where the database runs | Database name | What changes |
|---|---|---|---|
| Local dev | Native PostgreSQL 18 on Machine A (Redis and other stores via `backend/docker-compose.dev.yml`) | `teamora` | Local host/password in `.env` |
| Automated tests / CI | Throwaway `pgvector/pgvector:pg18` container per CI run | `teamora` | CI-only throwaway password |
| Staging | Remote: Coolify-managed PostgreSQL in the `staging` environment, internal network only | `teamora` | Staging credentials in Coolify env vars |
| Production | Remote: separate Coolify-managed PostgreSQL in the `production` environment (Patroni/HA is a later step, see charter) | `teamora` | Production credentials in Coolify env vars |

Because every environment uses the same name, a mistaken connection string no longer shows up in the name. These safeguards replace that:

- Every service reads `APP_ENV` (`local` / `test` / `staging` / `production`) and logs it together with the DB host at startup.
- Staging and production passwords are generated by Coolify, so they never match local ones. A local `.env` simply can't log in to a remote DB.
- The staging and production Postgres ports aren't published outside the Coolify server's internal Docker network.
- Destructive scripts (reset, seed, drop) refuse to run unless `APP_ENV=local` or `APP_ENV=test`.
- Local automated tests run against a **separate PostgreSQL instance or container** (e.g. port 5433), which is also named `teamora`, so a test run never wipes the local dev data.

### 1.2 Engine and version

- **PostgreSQL 18**, the same major version in every environment so local dev matches Machine A's native 18.6 install.
  Containers (CI, staging, production on Coolify) use the image **`pgvector/pgvector:pg18`**.
- Extensions: `vector` (Dedupe, TDD §16), `pgcrypto` (UUID generation), `citext` (case-insensitive email).

### 1.3 Database name

**`teamora`**, the same in every environment (rule 3 in §1.1).

### 1.4 One database per environment, one schema per service

TDD §17.1 says no service reads another service's tables. For Release 1 we enforce that with **one PostgreSQL database per environment and one schema per owning service**, each with its own login role.
This gives the same isolation as a database per service, but needs only one Coolify Postgres resource per environment.

| Schema | Owning service | Main tables (TDD §5–7) |
|---|---|---|
| `identity` | auth-service | tenant, client, user, tenant_sso_config, session audit |
| `requisition` | requisition-service | job_requisition, jd_brief, jd_field, jd_version, scoring_matrix, scoring_criterion, jd_template (see Blocker B3) |
| `sourcing` | publish-service | sourcing_channel_config, publish_job |
| `candidate` | candidate-service | candidate, application |
| `dedupe` | dedupe-service | duplicate_match, candidate_embedding (`vector` column) |
| `notification` | notification-service | template, delivery_log (the job queue itself is in Redis/BullMQ) |

Roles:

- Role names are the same in every environment; only their passwords differ.
- `teamora_migrator` owns every schema and is the **only** role that runs migrations.
- One app role per service (`svc_auth`, `svc_requisition`, …) gets `USAGE` plus DML on **its own schema only**.
- App roles are never table owners and never `BYPASSRLS`. PostgreSQL skips RLS for a table's owner unless `FORCE ROW LEVEL SECURITY` is set, so set it on every multi-tenant table.
- Tenant context is passed with `SET LOCAL app.tenant_id` and `SET LOCAL app.client_id` inside each transaction. RLS policies read them with `current_setting('app.tenant_id', true)`. If they aren't set, the query returns zero rows (TDD §5.3).

### 1.5 Migrations

Each service owns the migrations for its own schema and keeps them in its own folder. Two migration tools are therefore acceptable:

- NestJS services: **Drizzle ORM + drizzle-kit**. It handles `SET LOCAL` in transactions cleanly, which RLS needs. Prisma is awkward here.
- FastAPI services: **SQLAlchemy 2 + Alembic**, with `version_table_schema` set to the service's own schema.
- Shared bootstrap (create database, schemas, roles, extensions): plain SQL in `backend/db/init/`. The same scripts run everywhere: once with `psql` on the local native install, once on the staging/production instances, and automatically by the CI container. Passwords are passed in as variables and never written into the scripts.
- The same migrations run in every environment, in the same order. Staging and production run them as a deploy step, never by hand from a developer machine.

### Layout rules (follow these for every change)

**Rule 1: only these stay at the repo root.** Everything else goes inside `frontend/` or `backend/`.

| Root item | Why it has to be at the root |
|---|---|
| `.github/workflows/` | GitHub Actions only reads workflow files from this exact path |
| `.gitignore` | Applies to the whole repository |
| `.gitattributes` | Forces LF line endings so files edited on Windows still build on Linux (Coolify) |
| `README.md` | GitHub shows it on the repo's front page |
| `.editorconfig`, `.pre-commit-config.yaml`, `.nvmrc` | Repo-wide editor, commit-hook and Node-version settings |

A new top-level folder beside `frontend/` and `backend/` needs an explicit decision recorded in the charter first.

**Rule 2: each backend service deploys separately, and builds from `backend/`.**
`backend/` isn't one deployable; each service in `backend/services/` is its own Coolify application.
Every service's build context is `backend/`, not the service's own folder, because the image has to include the shared code in `backend/packages/` (TypeScript) or `backend/python-libs/` (Python).
Each service has its own Dockerfile at `backend/services/<service>/Dockerfile`, written with paths relative to `backend/`.

**Rule 3: watch paths decide what a change rebuilds.** Each Coolify application only redeploys when files under its own watch paths change:

| Coolify application | Base Directory | Dockerfile | Watch paths |
|---|---|---|---|
| frontend | `/frontend` | `Dockerfile` | `frontend/**` |
| auth-service | `/backend` | `services/auth-service/Dockerfile` | `backend/services/auth-service/**`, `backend/packages/**`, `backend/package-lock.json` |
| requisition-service | `/backend` | `services/requisition-service/Dockerfile` | `backend/services/requisition-service/**`, `backend/packages/**`, `backend/package-lock.json` |
| notification / publish / candidate-service (NestJS) | `/backend` | `services/<service>/Dockerfile` | `backend/services/<service>/**`, `backend/packages/**`, `backend/package-lock.json` |
| jd-generation / resume-parsing / dedupe-service (FastAPI) | `/backend` | `services/<service>/Dockerfile` | `backend/services/<service>/**`, `backend/python-libs/**` |

So a frontend-only change never redeploys the backend, and a change inside one service never redeploys the others.
A change to shared code (`backend/packages/**` or `backend/python-libs/**`) rebuilds every service that uses it, which is intended.
The same Base Directory, Dockerfile and watch paths apply to the staging and production applications of each service.

**Rule 4: frontend and backend never import each other's code.**
The only contract between them is the OpenAPI specs in `backend/packages/contracts/`.
The frontend generates its typed API client from those specs into `frontend/src/api/`, and never imports backend code.
When an API changes, update the spec in `backend/packages/contracts/` first, then regenerate the frontend client.
This is what keeps the two folders independent and each one deployable by itself.

- Branches: `feature/REQ-TMR-<id>-<slug>` off `staging`, PR back into `staging` (SOP §4.1).
